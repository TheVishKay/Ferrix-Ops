# ferrixOps: measurable engineering roadmap

These are proposed improvements and acceptance targets, not achieved results. Prefer a few completed, measured improvements over a larger feature list. A strong project story connects a manufacturing problem, an engineering decision, a controlled measurement and an actual operational outcome.

## Existing evidence to preserve

- Task creation changed from three service operations to one RPC: 67% less service-level request orchestration, excluding refresh/auth/retries.
- Route splitting reduced initial static JavaScript from about 1,262 KB to 501 KB (60%), and gzip from about 348 KB to 146 KB (58%). This is a bundle-size result, not a measured load-time improvement.
- The focused database suite passes 24 checks. An 8-worker exercise created 20 tasks with distinct positions and exactly one creation audit record each. This is a small local concurrency test, not evidence of production scale.

## Implementation sequence

1. **Make the current system credible:** verify deployment, remove misleading report counts, complete owner contacts/missing-day corrections and build the cross-role acceptance matrix.
2. **Measure and improve one bottleneck:** establish a versioned fixture and baseline, then optimize pagination/queries and capture page-performance data.
3. **Demonstrate backend depth:** add retry/idempotency and stale-write semantics, then mixed-concurrency and failure-injection tests.
4. **Prove usefulness:** run a small pilot and measure actual adoption, handling time, turnaround and error rates. Add reliable notifications or reporting in response to observed needs.

The strongest three outcomes to pursue are **actual operational time saved**, **measured query/interaction performance**, and **verified authorization/concurrency correctness**. Those give the project a useful product story and technical depth without requiring unrelated infrastructure or an artificial AI feature.

## Measurement rules

For every performance result record the commit SHA, fixture version/seed, row counts, database/runtime versions, test environment/region, concurrency, warmup, repetitions and raw results. Use at least 100 measured requests for an initial latency comparison, and larger samples when drawing tail-latency conclusions. Report distributions and failure counts, not just the fastest run. Use a monotonic clock for durations.

For percentage reductions, calculate `(baseline - new) / baseline × 100`. Keep latency reduction, throughput increase and byte reduction separate. For business outcomes, distinguish active users from registered accounts, handling time from approval waiting time, and synthetic workload from real transactions.

Store synthetic benchmark artifacts in a versioned `benchmarks/` directory when implemented. Keep actual employee records, contacts, receipts, tokens and raw identifiable telemetry out of the public repository; publish only appropriately anonymized aggregates.
