# FerrixOps engineering walkthrough

FerrixOps is an internal manufacturing operations platform for employee administration, attendance, leave, expenses, and tasks. The expense workflow illustrates how the React interface and PostgreSQL divide responsibility. The interface guides each person through their next action. Database grants, row-level security, and RPC checks govern the underlying records and transitions.

## Follow one expense from draft to paid

Use three synthetic accounts and the seeded **Equipment** category. The example is a ₹2,450 claim for a replacement torque wrench from **Demo Tool Supply**. Open **Bills & Expenses** (`/bills`) in each account and use the row's action menu as the claim progresses. [Demo setup](LOCAL_SETUP.md#seed-a-synthetic-expense-demo) · [React expense page](../src/pages/BillsExpenses.jsx)

1. **Employee saves and submits.** Choose **New Expense**, enter the claim, and choose **Save Draft**. Close the form, then choose **Submit** on the saved row. `create_expense` associates the draft with the signed-in user's active employee record. `submit_expense` locks the row, checks ownership and the current state, and sets it to `SUBMITTED`. The employee can follow their own claim in the list. [Expense creation RPC](../supabase/migrations/20260831000400_security_and_functions.sql#L844) · [Current submission RPC](../supabase/migrations/20260906000004_audit_operations.sql#L13)
2. **Accounts reviews.** The submitted row appears under **Needs My Action** with **Review (Accounts)**. Approving via `review_expense_accounts` moves it to `PENDING_OWNER_APPROVAL`. Accounts can also reject the claim or return it with remarks for correction. A returned claim can be edited and resubmitted by its submitter. Accounts' review policy exposes non-draft expenses, with a separate own-expense policy path for their own drafts. [Accounts review RPC](../supabase/migrations/20260906000004_audit_operations.sql#L74) · [Current read policies](../supabase/migrations/20261104000001_optimize_expense_read_policies.sql)
3. **Owner gives final approval.** The Owner can see all expense rows and gets **Review (Owner)** on this pending claim. `review_expense_owner` locks the row and requires `PENDING_OWNER_APPROVAL` before approval moves it to `PAYMENT_PENDING`. [Owner review RPC](../supabase/migrations/20260906000004_audit_operations.sql#L173)
4. **Accounts records the payment.** Open **Record Payment**, select **Bank Transfer**, and use a fake external reference such as `DEMO-TRANSFER-001`. The app records a payment made outside FerrixOps. `record_payment` locks the approved expense, takes the amount from the stored claim, and inserts the payment, marks the claim `PAID`, and records an audit event in one transaction. A uniqueness constraint on the expense ID backs the duplicate-payment check. The employee can now see **Paid** on their claim. [Payment RPC](../supabase/migrations/20260906000004_audit_operations.sql#L255) · [Payment schema](../supabase/migrations/20260831000300_expenses_and_payments.sql#L332)

## Why task updates moved into PostgreSQL

A client that separately reads a task, updates its status, and writes an audit event can act on a stale status or leave a changed task with no audit entry if the last request fails. FerrixOps puts the transition and audit into one database call, with direct task writes removed from the authenticated client's grants. [Task RPC migration](../supabase/migrations/20261002000001_tasks_rpc_and_audit.sql) · [Task read grant](../supabase/migrations/20261002000002_grant_tasks_select.sql)

Consider an assignee moving **Inspect conveyor guard** from `IN_PROGRESS` to `READY_FOR_REVIEW`.

1. The task board calls `taskService.updateTaskStatus`, which sends the task ID and requested status to `update_task_status`. The function resolves the caller's profile role from the authenticated identity and rejects a missing role. [Task board](../src/pages/Tasks.jsx) · [Task service](../src/services/taskService.js#L118)
2. The function reads the task with `SELECT … FOR UPDATE`. A concurrent change to the same row waits for the first transaction. The function checks the target against the allowed status values. The Owner can select any valid status, while other callers need an active employee record, the assignment, and a permitted transition from the locked status. [Status RPC](../supabase/migrations/20261002000001_tasks_rpc_and_audit.sql#L17)
3. The function updates the status and timestamp, writes `TASK_STATUS_UPDATED` with the actor and before/after status, and returns the updated row. A failure writing the audit event rolls back the mutation. A second assignee request for `READY_FOR_REVIEW` checks the newly committed state and fails transition validation. [Status RPC and audit call](../supabase/migrations/20261002000001_tasks_rpc_and_audit.sql#L95)

The disposable PostgreSQL regression suite covers task read isolation, assignment and transition checks, the status audit event, and the concurrent status update. It separately forces an audit failure during task creation and checks that the insert rolls back. [Regression suite](../scripts/test_task_database.py#L121) · [CI workflow](../.github/workflows/ci.yml)

## What sped up expense reads

The original Owner and Accounts SELECT policies called `get_my_role()` directly. This helper looks up the signed-in user's role and takes no expense-row input. The final migration wraps the calls in scalar subqueries. In the recorded plans PostgreSQL used InitPlans to evaluate the role once per statement. Both variants retained the same permissions, row-visibility rules, and indexes. An earlier index-only diagnostic showed no benefit in its one completed pair. [Policy migration](../supabase/migrations/20261104000001_optimize_expense_read_policies.sql) · [Investigation and plans](ferrixOps_API_BENCHMARK_RESULTS.md)

The harness alternated baseline and candidate order across five paired runs in a temporary local Supabase stack. Both variants used the same synthetic dataset, authenticated Owner workload, and keyset-paginated PostgREST queries. The harness checked access and response correctness before timing and checked each measured response against an expected digest. Across 10,000 synthetic expenses and 20 virtual clients, median run-level p95 fell from **104.9 ms to 35.9 ms**. All three deep-page classes regressed by roughly 14–16 ms at p95. The result measures the local benchmark's query mix. The browser currently uses a different list query.
